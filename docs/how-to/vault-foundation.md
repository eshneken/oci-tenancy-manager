# Vault custody and database-reader IAM foundation

**Implemented Terraform source; live qualification Pending.** The new `security` roots create
shared Vaults, HSM-protected master keys and one scoped database-reader IAM
policy. They create no secrets, passwords, memberships, federation or application deployment.
No live OCI resources or saved Atlas instance were changed during development.

## One hosting compartment, two Vaults per environment

| Domain | Purpose | Authority added by this slice |
| --- | --- | --- |
| `database-provisioning` | Initial PostgreSQL administrator credential; privileged provisioning/recovery custody | Approved existing provisioning group can read secret-family and Vault metadata only in this Vault |
| `application-secrets` | Future runtime database credentials and managed parent/child credential custody | No application or provisioning-group grant is added yet |

`infra/modules/secret-foundation` creates two DEFAULT shared Vaults and a separate HSM-protected
AES-256 master key for each, all in the existing hosting compartment selected through
`OTM_HOSTING_COMPARTMENT_OCID`. It creates **no child compartments**. Vault/key `prevent_destroy`
guards remain. No secret-content resource, secret-bundle lookup, password generator, key export or
plaintext input is present. Master key material is generated by OCI.

Exact Vault-ID conditions provide the IAM scope inside the shared compartment. Separate Vault
names alone are not an authorization boundary; both reader policy statements must retain the
condition targeting the database-provisioning Vault. OCI documents a
[Vault-filtered secret-family read policy](https://docs.oracle.com/en-us/iaas/database-management/doc/additional-permissions-required-use-database-management-external-databases.html).
Live secret/bundle/version read and denial tests remain required; do not remove the condition to
make a missing permission work.

The default shared Vault tier avoids allocating a dedicated virtual-private HSM partition. Actual
key usage, quotas, cost and availability still require live qualification. Automatic KMS master-key
rotation is explicitly disabled here: [Oracle documents automatic rotation as a virtual-private Vault feature](https://docs.oracle.com/en-us/iaas/Content/KeyManagement/Tasks/tasks_tasks_managingkeys_topic_edit_auto_key_rotation.htm).
Shared-Vault keys require an owned manual key-version rotation procedure and qualification before
go-live. This is separate from OTM's child signing-key/password rotation jobs. Preserve old key
versions needed to decrypt retained secrets; never assume rotating a key rewrites every stored secret.

## Deployment order and separate state

The platform database needs an existing secret reference, so the custody foundation must precede
platform creation. A separate root avoids routine `terraform -target`, dummy passwords or a dependency
cycle. Staging and production each have their own root, provider identity, state and resources:

| Root | Fixed private OCI backend key |
| --- | --- |
| `infra/environments/staging/security` | `security/staging/terraform.tfstate` |
| `infra/environments/production/security` | `security/production/terraform.tfstate` |

1. Render the selected environment's [hosting compartment input](hosting-compartment.md) and
   complete the [state bucket bootstrap](terraform-state-bootstrap.md) in that same compartment.
2. Verify the hosting compartment, current principal, namespace, approved reader group and ancestry
   independently in that tenancy. Format checks and a matching environment/namespace do not prove IAM
   isolation or resource ownership. Staging and production use separate identities and group bindings.
3. Review and create the security resources using the procedure below. Verify the existing hosting compartment,
   Vault ACTIVE state, enabled HSM keys and the exact policy in OCI; allow for IAM propagation.
4. A separately authorized secret custodian securely creates the strong provisioning password in the
   **database-provisioning Vault**, using its key in the same hosting compartment. Use the OCI Console or another approved
   secure ingestion process. Do not put secret payloads in Terraform, shell arguments, logs, chat,
   public artifacts or a repository file. Record only its OCID and explicit version in private custody.
5. Supply that exact reference/version as `database_administrator` when planning the
   [managed PostgreSQL platform](managed-postgresql.md). Independently verify the reference's tenancy,
   hosting compartment, Vault/key and usable version before applying. This slice does not automatically read
   or import security remote state into platform state.
6. Runtime database roles, application workload identity and scoped secret access follow separately.
   Application deployment never requires permission to read security Terraform state or the initial
   database administrator password.

For each environment, copy `terraform.tfvars.example` to a private `target.tfvars` and
`backend.tfbackend.example` to a private `security.tfbackend`, outside the checkout. Replace only
synthetic nonsecret coordinates/profile/group references. The `target` fields and explicit
SecurityToken/ResourcePrincipal/InstancePrincipal provider choices follow the existing
[network authentication rules](network-foundation.md). There is no long-lived API-key fallback.
The OCI backend's SecurityToken profile remains a separate consumer from provider authentication.

The group field `database_provisioner_group_ocid` is required and accepts only a group OCID. It
must identify the approved existing privileged credential readers in that environment; no group,
member or trust is created by this module. The root fixes the staging/production environment and
backend key. Do not override that key, use Terraform workspace names to switch environments or
initialize a second state against the same resources.

### Operator-reviewed staging commands

Render `hosting.tfvars.json` into the private directory using the hosting-input guide.
Run from the repository root after replacing the private directory and authenticating the approved
operator. Keep its directory owner-only, private files under `umask 077`, shell tracing/TF_LOG off,
and all state/plans/outputs out of public logs and artifacts:

```sh
umask 077
export OTM_SECURITY_DIR=/absolute/private/path/otm-staging-security
export TF_DATA_DIR="$OTM_SECURITY_DIR/provider-data"
terraform -chdir=infra/environments/staging/security init \
  -input=false -lockfile=readonly \
  -backend-config="$OTM_SECURITY_DIR/security.tfbackend"
terraform -chdir=infra/environments/staging/security plan \
  -input=false -var-file="$OTM_SECURITY_DIR/target.tfvars" \
  -var-file="$OTM_SECURITY_DIR/hosting.tfvars.json" \
  -out="$OTM_SECURITY_DIR/security.tfplan"
terraform -chdir=infra/environments/staging/security show \
  "$OTM_SECURITY_DIR/security.tfplan"
```

Expect exactly two shared Vaults, two AES-256 keys and one Vault-conditioned policy in the existing
hosting compartment, with no compartment, secret, VM, database, group or membership creation.
Stop on unexpected scope, deletion or
replacement. After approval, apply the **same saved plan** and export only the private references:

```sh
terraform -chdir=infra/environments/staging/security apply \
  -input=false "$OTM_SECURITY_DIR/security.tfplan"
terraform -chdir=infra/environments/staging/security output -json custody \
  > "$OTM_SECURITY_DIR/custody.json"
```

The sensitive output contains environment, the two domains' compartment/Vault/key OCIDs and the
reader policy OCID. It contains no password, private key or secret bundle. Sensitive means ordinary
output redaction, not state encryption or authorization. Production repeats the procedure with its
own root, approved inputs, private paths and credentials after staging qualification; never apply a
staging saved plan or reuse its IDs in production.

## Exact IAM limits

The policy is attached to the existing hosting compartment and grants the supplied group `read
secret-family` and `read vaults` in that compartment, each with the exact condition
`where target.vault.id = '<database-provisioning Vault OCID>'`. Neither grant covers the other Vault.
These are the requester-side permissions documented in
[OCI PostgreSQL policies](https://docs.oracle.com/en-us/iaas/Content/postgresql/policies.htm).
Secret-family read includes access to secret contents: this group is privileged credential custody,
not an ordinary application or UI-administrator group.

There are no write/delete/move grants, no direct key-decrypt grant, no tenancy-wide grant, no
application-secret grant, and no invented PostgreSQL service principal. Group membership,
PostgreSQL/network deployment authority and the custodian's secret creation/key-use permissions must
already be supplied through separately approved IAM. The provisioning reader policy by itself
cannot ingest or rotate secrets, create a DB or perform infrastructure deployment.

OCI policies are additive. Existing tenancy/ancestor grants may already confer broader authority;
these source statements cannot prove effective isolation. Live negative tests must check application
workloads cannot read initial database credentials and that provisioning readers cannot mutate/delete
secrets or read application-Vault secrets through other grants. Future OKE workload policies must
bind exact cluster, namespace and service account, with no node/parent credential fallback.

## Protection and qualification

Vault/key loss or access revocation can make dependent secrets and recovery unusable. Terraform
replacement guards do not block direct OCI administration, key disable/deletion, configuration removal,
or a privileged change that removes the guard. Preserve private state and key-version custody and
verify actual backup/recovery dependencies. This foundation does not automatically back up Vaults,
provide cross-region DR or repair lost keys after a database restore.

Run `bash scripts/check_infrastructure.sh` without OCI credentials. The thirteen native configuration
suites use mock providers and `init -backend=false`. Tests check exact policy text, distinct custody
domains, HSM key/Vault bindings, invalid input rejection and fixed roots. Two additional negative
journeys require mock setup followed by the exact protected resource's lifecycle rejection for Vault
and key replacement. They do not evaluate OCI's effective IAM or decrypt real secrets.

Follow the [pending live Vault/IAM qualification](real-oci-test-manifest.md#vault-custody-foundation)
for actual group/policy scope, custody ingestion, read denial, key rotation/decryption, state controls
and PostgreSQL provisioning. Full required application/milestone checks still precede the combined
PR; source checks are not a deployed service or production security qualification.
